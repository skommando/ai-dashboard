# AI 工作台与远程项目进度看板：简要调研

调研日期：2026-09-28。依据项目官方仓库与产品文档，未安装试跑或审计实现。下文“与本项目的关系”和设计建议为本次分析，不是已经批准的产品方案。

## 主要发现

“AI 工作台”覆盖多种产品。就本次六个样本而言，Happy 和 CloudCLI 最接近离开电脑后用手机查看本机 AI 工作的场景；Vibe Kanban 和 OpenHands/Agent Canvas 更偏任务组织与执行；Open WebUI 和 Dify 则分别偏模型交互、AI 应用搭建。

本项目希望进一步统一不同项目的进度计量、主动上报和手机概览。这些样本的官方简介没有将这一整套要求作为核心能力描述，因此不能仅凭“有看板”或“支持 MCP”认定它们可直接替代本项目；具体扩展能力仍需在选型后验证。

| 项目与一手来源 | 官方描述的主要功能 | 与本项目的关系（分析） |
| --- | --- | --- |
| [Open WebUI](https://github.com/open-webui/open-webui) | 多模型聊天、知识库/RAG、工具扩展、自动化、使用量分析，支持手机与 PWA | 可借鉴移动端体验；主要组织模型交互、知识和工具，项目完成度仍需另外建模 |
| [Dify](https://github.com/langgenius/dify) | 可视化 AI 工作流、Agent、知识检索、模型管理和运行观测 | 更适合搭建 AI 应用；其工作流执行状态与跨仓库项目交付进度是不同粒度 |
| [OpenHands / Agent Canvas](https://github.com/OpenHands/OpenHands) | 自托管编码 agent 控制台，连接本地/远程/云端执行环境，并提供自动化 | 可借鉴多项目与执行状态组织；执行与自动化范围比当前只读看板目标更大 |
| [Vibe Kanban](https://github.com/BloopAI/vibe-kanban) | 任务看板、编码 agent 工作区、差异审查、预览和 PR 流程 | 可借鉴任务和验收组织；运行任务看板不直接等于统一完成度，且维护方式已发生变化，见下文 |
| [CloudCLI / Claude Code UI](https://github.com/siteboon/claudecodeui) | 浏览器与手机查看项目/会话，交互聊天、终端、文件和 Git 管理，可选任务管理集成 | 与远程查看很接近；主要围绕编码工具会话，通用项目上报和统一计量仍需补充 |
| [Happy](https://github.com/slopus/happy) | Claude Code/Codex 的 iOS、Android 与 Web 客户端，远程会话查看/控制、通知和加密同步 | 与“拿起 iPhone 看 AI 在做什么”最接近；通常经其 CLI 包装器启动会话，面向会话的视图与项目交付计量仍有差别 |

Vibe Kanban 官方在 **2026-04-10** 宣布关闭背后的 bloop 公司，项目继续开源并转由社区维护。公告称远程服务保留 30 天后撤下，本地工作区继续可用。此处确认的是公告内容，未实际探测远程服务当前状态；适合作为交互参考，采用前应重新核对社区版本的功能与维护情况。[官方公告](https://www.vibekanban.com/blog/shutdown)

## Windows 与 iPhone 的可行路线

**建议首版使用响应式 Web，并提供 PWA 体验。** Windows 运行服务，iPhone 用 Safari 访问并添加到主屏幕即可像 App 一样打开；这条路线不需要编译 iOS 安装包。Apple 官方提供了“添加到主屏幕”和“作为网页 App 打开”的操作说明。[Apple 文档](https://support.apple.com/zh-cn/guide/iphone/iphea86e5236/ios)

Windows 开发也并非完全不能产出原生 iOS 应用。Xcode 的官方运行环境是 macOS；可采用远程 Mac 或云构建，例如 Expo 明确支持从任意电脑发起 iOS 云构建。是否采用这条路线还涉及原生客户端实现、签名和分发，当前查看需求无需先引入这些工作。[Xcode 系统要求](https://developer.apple.com/xcode/system-requirements)、[Expo 构建说明](https://docs.expo.dev/more/expo-cli/)

“手机能打开页面”与“外网能连接本机”需要分别解决：设计时还需选择局域网、VPN 或受保护的远程入口。若服务与数据都留在 Windows 本机，本机休眠或断网时就无法提供最新状态，应在查看端明确显示不可达或数据陈旧。

## 后续设计建议（未定稿）

### 统一语义，再提供不同调用入口

建议用同一份数据模型和计算逻辑支撑 HTTP API 与 MCP 工具：脚本和普通应用通过 HTTP 更新，AI agent 可通过 MCP 更新，查看端读取同一份进度数据。

OpenAPI 用于描述 HTTP API；MCP 则可将操作暴露为 AI 应用可调用的工具，二者可以同时采用。建议先定义最小的项目、任务、运行实例、进度事件和查询语义，再按首批接入者需要提供接口，不先建设庞大的通用平台。[OpenAPI 规范](https://spec.openapis.org/oas/latest.html)、[MCP 服务端概念](https://modelcontextprotocol.io/docs/learn/server-concepts)

### 进度至少拆成三个维度

| 维度 | 首版建议 | 需要防止的误读 |
| --- | --- | --- |
| 完成度 | 当前计划中，达到事先约定完成标准的任务权重之和 ÷ 总任务权重；同时展示完成数/总数 | 不把 token、运行时长、提交数或 agent 主观估计直接当作项目完成率；没有有效分母时显示未知 |
| 工作状态 | 当前阶段、正在做什么、运行中/等待用户/阻塞/完成/失败等状态与原因 | “进程活着”不代表“项目正在推进”；实现完成与人工验收分别记录 |
| 数据新鲜度 | 最近一次进度更新时间、独立心跳和连接/陈旧标记 | 心跳可以持续更新而任务没有进展；停止上报不能默认为完成，也不能直接认定项目失败 |

该百分比表达的是**各项目当前计划的完成比例**，不保证两个项目的 50% 对应相同工作量或剩余时间。调整计划范围时记录版本与变化原因，允许完成率随分母变化而下降。首版可对规模相近的任务采用等权，只有实际需要时再引入不同权重。

### 手机首页的信息优先级

项目名、当前阶段、完成度、阻塞/待处理事项、最后更新时间应直接可见；详情页再展开任务和运行记录。优先呈现需要用户处理的项目，同时显示明确文字状态，避免仅靠颜色或完整终端日志表达进展。

当前将“终端兼容”理解为手机与桌面设备适配。如果另需 SSH/命令行终端查看，可后续提供同一查询 API 的 CLI/TUI 客户端，不影响上述进度模型。

下一步设计最需要明确的是：首批接入哪些项目/agent、采用什么任务完成依据，以及 iPhone 是否需要在外网访问。本次未安装这些产品、未部署服务，也未将上述建议视为实施批准。
